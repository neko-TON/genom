# Nostro Capital — бэкенд-узел для готового фронтенда

Дата: 2026-08-29. Статус: одобрен пользователем (устно, в чате).

## Контекст и цель

Из архива `nostro.capital.zip` получен готовый фронтенд сайта проекта
**Nostro Agent ($NSTRO)** — индексный токен, которым управляет автономный агент
внутри жёстких лимитов контракта:

- `index.html` + `front.css` + `front.js` — лендинг с живой строкой данных;
- `console.html` + `app.css` + `app.js` — консоль: корзина, график NAV,
  track record c keccak-коммитами, холдеры, казна, governance, лог;
- `favicon.svg`, `brand-banner.jpg`.

Обе страницы опрашивают бэкенд (`/api/state` и др.), которого в архиве нет.
При его отсутствии лендинг вечно пишет «CONNECTING», консоль пуста; сам фронтенд
подсказывает: «NODE OFFLINE — RUN: python3 server.py».

**Цель:** достроить недостающий бэкенд, чтобы сайт работал целиком, локально,
одной командой. Фронтенд из архива не изменяется (остаётся байт-в-байт);
бэкенд подстраивается под его контракт.

**Решения пользователя:** объём — симуляция **и** live-режим; работа — пока
только локально; реальных контрактов ещё нет (live — «про запас», проверяем на
любом существующем токене сети); стек — вариант A, чистый Python без зависимостей.

## Структура проекта

```
~/nostro.capital/
  index.html, console.html, front.css, front.js,
  app.css, app.js, favicon.svg, brand-banner.jpg   ← из архива, без изменений
  server.py            ← весь бэкенд-узел (один файл, только stdlib)
  nstro                ← CLI-скрипт (исполняемый)
  nstro.json           ← конфиг режима; создаёт CLI; в .gitignore
  tests/test_server.py ← unittest, без зависимостей
  README.md            ← запуск и управление, по-русски
```

Запуск: `python3 server.py` → `http://localhost:8000` (порт меняется флагом
`--port`). Python ≥ 3.9, ничего устанавливать не нужно.

## Архитектура server.py

Один процесс, четыре части:

1. **HTTP** — `ThreadingHTTPServer` + `BaseHTTPRequestHandler`: статика из
   папки проекта и JSON API (контракт ниже).
2. **Поток симуляции** — тик ~4 раза/с; симуляционное время течёт со скоростью
   `speed` сим-секунд на реальную секунду. По умолчанию эпоха (24 ч сим) = 60 с
   реальных (`speed = 1440`); из консоли переключается 15/60/180 с, там же
   пауза и ручное закрытие эпохи. Состояние — в памяти под одним замком
   (mutex); рестарт сервера = свежая симуляция. Флаг `--seed N` фиксирует RNG
   для воспроизводимости.
3. **Поток live-поллера** — активен только в режиме live; раз в 4 с опрашивает
   цепочку по JSON-RPC (`urllib`), кладёт снапшот в состояние. Следит за mtime
   `nstro.json` — режим переключается без рестарта сервера.
4. **Крипто** — keccak256 (компактная реализация keccak-f[1600] на чистом
   Python; хешируем раз в эпоху, скорость не важна) и `abi.encode` с семантикой
   Solidity для сигнатуры `(uint256, uint256[], string, bytes32)`.
   Коммит агента: `keccak256(abi.encode(epoch, weights, thesisText, nonce))` —
   как заявлено на сайте («genuine keccak256 + abi.encode»).

## Контракт API (выписан из front.js / app.js, менять нельзя)

### GET /api/state — общие поля

| поле | тип | смысл |
|---|---|---|
| `mode` | `"sim" \| "live"` | режим узла |
| `public` | bool | публичный узел: симуляция скрыта (у нас всегда `false`; флаг `--public` есть, но по умолчанию выключен) |
| `config.rpc_url` | str | RPC для кнопки «add chain» в кошельке |

### GET /api/state — режим симуляции

- `epoch` int, `t` сим-секунды, `phase` 0–3, `paused` bool,
  `speed` float, `epoch_progress` 0..1;
- `nav` USDG, `unit_value`, `unit_values[]` (по эпохам), `shadow_uv[]`
  (теневая траектория агента без исполнения);
- `weights` {SYM: bps, сумма 10000, включая USDG}, `prices` {SYM: usd};
- `pending_quote` USDG (очередь на батч-покупку), `volume_epoch` USDG;
- `epochs[]`: `{n, dnav_pct, checks[{name, ok, detail}], cancelled: str|null,
  executed: bool, turnover_bps, exec: {trades[{asset, value, impact_bps}],
  max_impact_bps, cost} | null, phase}`;
- `track[]`: `{epoch, hash "0x"+64hex, revealed, verified, thesis (после
  reveal), committed_at, revealed_at: t|null}`;
- `holders[]`: `{id, name, kind: "user"|"sniper"|"", balance, last_share 0..1,
  claimable_value, claimed_value}`; кошелёк пользователя — `id == "you"`;
- `treasury`: `{runway_days, usdg, epoch_cost, inflow_tax, inflow_creator,
  protocol_fund, hold_mode}`;
- `guard`: `{frozen, freeze_epoch, limits: {max_weight_bps, turnover_bps}}`;
- `gov_queue[]`: `{label, action, eta}` (eta — эпоха исполнения);
- `log[]`: `{t, msg}` (английский — показывается на сайте).

### GET /api/state — режим live

- `live`: `{ok, error?, kind: "token"|"vault", chain_id, block, name, symbol,
  decimals, code_size, total_supply, vault, ...}` — плюс best-effort-поля
  `pons{}`, `fee_vault{}`, `commits{}`, `basket{}`, `linked{}`, `current_epoch`,
  `nav`, `units`. Отсутствующие просто опускаются — фронтенд везде проверяет
  `!= null`.
- `real` — исторические данные (эпохи, холдеры из Transfer-логов). Без реальных
  контрактов Nostro не заполняется — фронтенд тогда скрывает эти карточки.

### Остальные эндпоинты

- `POST /api/control` `{action: "pause"|"resume"|"advance"|"speed", value?}` —
  value для speed — секунд на эпоху (15/60/180);
- `POST /api/trade` `{side: "buy"|"sell", amount}` — сделка кошелька «you»;
- `POST /api/claim` `{}` — клейм начислений «you»;
- `POST /api/gov` `{action: "phase3"|"unfreeze"}` — поставить голосование в
  очередь с таймлоком;
- `GET /api/claims?address=0x…` — merkle-клеймы live-режима; без реального
  дистрибьютора: `{distributor: null, rounds: []}`.

Все POST отвечают `{ok: true}` (или `{ok: false, error}`); фронтенд ответ не
разбирает, а просто перезапрашивает состояние.

## Модель симуляции

**Активы.** Вайтлист: AAPL, TSLA, NVDA, MSFT, AMZN, GOOGL, META, HOOD, COIN,
PLTR + кэш USDG. Цены — геометрическое случайное блуждание с мягкими трендами,
обновление на каждом тике.

**Цикл эпохи (24 ч сим-времени).**

1. За 12 сим-секунд до закрытия снайпер-бот покупает 800k $NSTRO (его доля
   эпохи ≈ 0 — начисление идёт по балансу × времени, это ключевая демонстрация).
2. На закрытии эпохи N: подводятся итоги начислений
   (`share_i = ∫balance_i·dt / ∫supply·dt`), распределяется 80 % налога;
   раскрывается и сверяется тезис эпохи N (reveal → `verified`);
   агент строит вектор весов и тезис на эпоху N+1, генерирует nonce и
   запечатывает commit **до** любого исполнения.
3. MandateGuard гоняет 8 проверок нового вектора: вайтлист; вес ≤ лимита фазы;
   позиция ≥ 5 % либо 0; оборот ≤ лимита фазы; один ребаланс за эпоху;
   кэш 0–100 %; сумма весов = 100 %; агент не заморожен. Провал любой —
   эпоха отменяется (`cancelled` с причиной), корзина не двигается.
4. Если фаза ≥ 2 и вектор принят — батч-исполнение: сделки с price impact
   (bps) и стоимостью, `executed = true`. В фазах 0–1 исполнения нет (shadow).

**Демо-события.** Раз в ~10 эпох агент нарочно подаёт плохой вектор (вес выше
лимита или актив вне вайтлиста) — отклонение видно в track record и карточке
guard. Reveal всегда сходится (хеш считается честно, подделки нет).

**Экономика.** Фоновая торговля ботов + сделки пользователя дают
`volume_epoch`; 3 % налога делятся 80/13/7 (корзина/казна агента/протокол),
плюс 1 % creator fees в USDG в казну. Казна тратит `epoch_cost`
(inference + gas); `runway = usdg / epoch_cost`; при < 14 дней — hold mode
(ребаланс раз в 3 эпохи, предупреждение в консоли).

**Брейкер.** Просадка unit value от максимума за окно 7 эпох ≤ −25 % → агент
заморожен, корзина конвертируется в USDG, `guard.frozen = true`. Разморозка —
только голосованием.

**Governance.** `phase3` (доступно в фазе 2) и `unfreeze` встают в
`gov_queue` с таймлоком 3 эпохи (`eta`), по наступлении — исполняются и
пишутся в лог.

**Фазы (сжаты для демо).** P0 passive: эпохи 1–2, статичные веса, агент молчит.
P1 shadow: эпохи 3–8, коммиты и теневой график без исполнения. P2 reduced:
с эпохи 9, исполнение при лимитах вес ≤ 20 % / оборот ≤ 7 % NAV. P3 full
(35 % / 20 %) — только через голосование пользователя.

**Кошелёк «you».** Начинает с балансом $NSTRO и накапливает начисления как все;
`buy`/`sell` меняют баланс (и объём эпохи), `claim` переносит `claimable_value`
в `claimed_value`. Кнопка claim в консоли активна при `claimable_value > 0`.

## Live-режим

- CLI: `./nstro connect <адрес> [rpc]` пишет `nstro.json`
  (`{"mode": "live", "vault": "0x…", "rpc_url": "…"}`); `./nstro sim`
  возвращает симуляцию; `./nstro status` печатает текущий режим и состояние
  узла. Дефолтный RPC зашивается в CLI, если на этапе реализации найдётся
  работающий публичный RPC Robinhood Chain (проверяется запросом
  `eth_chainId` == 4663); если нет — аргумент `rpc` обязателен, CLI прямо об
  этом говорит.
- Определение вида контракта probe-вызовами `eth_call`: отвечает
  `previewUnits(address)` → `kind: "vault"`, иначе ERC20 → `kind: "token"`.
- Читается стандартное: `eth_chainId`, `eth_blockNumber`, `name/symbol/
  decimals/totalSupply`, `eth_getCode` (размер), балансы fee vault
  (адрес зашит во фронтенде). Специфика Pons и merkle-дистрибьютор — только
  best-effort; недоступные поля опускаются.
- Любая ошибка RPC → `live: {ok: false, error: "…"}` — фронтенд покажет
  «chain unreachable». Поллер продолжает попытки.
- Действия кошелька (buy/sell/feed/claim) в live-режиме фронтенд выполняет сам
  через MetaMask — серверу для них ничего не нужно.

## Ошибки и граничные случаи

- Битый JSON, неизвестный `action`/`side`, отрицательные суммы → 400 с
  `{ok: false, error}`.
- Поток симуляции обёрнут в try/except: исключение логируется в stderr, тик
  пропускается, симуляция не умирает.
- Занятый порт → понятное сообщение («порт занят, укажите --port»).
- Ctrl+C — чистая остановка обоих потоков.
- `nstro.json` отсутствует или битый → режим sim по умолчанию.

## Тестирование

1. **Крипто:** keccak256 на эталонных векторах (пустая строка →
   `0xc5d2…a470`, "abc", длинные входы); `abi.encode(uint256, uint256[],
   string, bytes32)` против векторов, полученных из Solidity/ethers.
2. **Инварианты симуляции** (гоняем движок синтетически, без HTTP):
   сумма весов всегда 10000 bps; отклонённый вектор не меняет корзину;
   доля снайпера за эпоху < 0.5 %; принудительная просадка −25 % включает
   брейкер, а голос unfreeze с таймлоком выключает; сумма выплаченных клеймов
   ≤ притока 80 %-й доли налога.
3. **Смоук API:** `GET /api/state` содержит все поля из контракта выше;
   POST-эндпоинты отвечают и меняют состояние.
4. **Живая проверка в браузере** (обязательна перед сдачей): лендинг получает
   данные (строка, лента, mini-basket, commit-терминал), в консоли живы все
   карточки, работают пауза/скорость/advance, trade/claim, голосование;
   пользователю показываются скриншоты.
